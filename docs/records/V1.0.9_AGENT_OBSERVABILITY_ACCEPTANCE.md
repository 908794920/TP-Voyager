# TP-Voyager v1.0.9 Agent Observability Acceptance

Date: 2026-08-19
Baseline: `v1.0.8` / `58d49e8`
Target: `v1.0.9`

## Scope

v1.0.9 adds the first usable **Observable Agent Runtime** experience without changing TP-Voyager's durable control-plane ownership.

Delivered:

- read-only `render_voyager_panel(task_id=...)` Captain MCP tool;
- self-contained MCP Apps UI resource at `ui://tp-voyager/agent-panel/v1.html` with MIME `text/html;profile=mcp-app`;
- obvious state dot / colored border / active pulse for queued, connecting, running/observing, completed, failed, cancelled, lost and orphaned states;
- expandable Conversation, Timeline, Files and Usage views;
- bounded Provider-visible assistant output from Qoder ACP and CodeBuddy Agent SDK callbacks;
- safe Tool/File activity projection and Provider-reported Usage projection;
- current-process, in-memory observation stream only; no new SQLite schema and no content-bearing durable transcript store;
- Codex host integration package under `skills/tp-voyager-captain/integrations/codex/` with a local marketplace and skills-only `tp-voyager-observability` plugin;
- existing TP-Voyager MCP registration remains owned by the existing install/sync path; the plugin deliberately contains no `.mcp.json` or `.app.json`, so it cannot start/register a duplicate Runtime.

The original six Captain tools keep their existing control/query behavior. v1.0.9 adds the seventh read-only visibility tool only.

## Data and security boundary

Durable SQLite Task / Session / Attempt / Event / Evidence / Artifact state remains authoritative. Agent UI observations are non-authoritative and disappear when the Runtime process restarts.

The observation projection accepts only allow-listed fields. It may show:

- Provider-visible assistant text;
- safe tool name/status/action metadata;
- workspace-relative file paths;
- Provider-reported usage values;
- safe terminal categories.

It does not admit:

- delegated Prompt text or system messages;
- credentials/secrets;
- raw tool output;
- absolute host paths or path traversal;
- hidden/private chain-of-thought.

A Provider-visible reasoning summary can be represented by the projection when a backend explicitly supplies one as user-visible data, but v1.0.9 does not attempt to extract private reasoning.

## Current-conversation behavior

The UI is deliberately task-pinned rather than a global Runtime dashboard:

1. `task_dispatch` returns the delegated `task_id` normally and references the Agent panel resource, so an MCP Apps-capable host can render presence immediately from that same dispatch result.
2. The MCP App pins itself to that exact returned `task_id`.
3. Refresh uses read-only `tools/call` to `render_voyager_panel(task_id=<returned id>)`; it never calls `task_dispatch`.
4. Calling `render_voyager_panel` without a `task_id` returns an empty `current_conversation` state instead of selecting recent tasks from another session.

MCP does not provide TP-Voyager with a portable Codex-native conversation identifier, so v1.0.9 enforces conversation locality through the explicit `task_id` handed back to the current host workflow rather than inventing a second session identity.

## Codex UI boundary

The implementation is an **in-conversation MCP Apps panel**. It does not populate, replace, imitate or modify Codex's native subagent list, and it does not alter Codex subagent routing.

Both `task_dispatch` and `render_voyager_panel` reference the same `_meta.ui.resourceUri`: dispatch linkage provides immediate Agent presence, while all UI-originated refreshes call only the read-only render tool. The component contains no path that calls `task_dispatch`, so refresh cannot become another dispatch path.

The UI has no external script/style/image dependency, no `localStorage`, and declares empty MCP Apps `connectDomains` / `resourceDomains` allow-lists.

## Automated verification in the build sandbox

Verified:

```text
python -m compileall -q agent_runtime skills/tp-voyager-captain
```

The sandbox does not have the real `mcp` package, so the regression suite was run with a minimal local FastMCP test stub that implements only the decorator/registration surface (`tool`, `resource`, `run`). This keeps Runtime/application behavior testable without pretending to validate the real MCP host transport. Tests were split only to stay inside the sandbox command timeout.

Result: **461 regression tests passed, 0 failed** across all 50 test modules, including the 11 long-running lease/reconciliation stress tests.

Also verified:

- plugin/marketplace/Captain manifest JSON parses successfully;
- observation stream does not write the supplied filesystem root;
- render without `task_id` does not auto-select a Runtime task;
- the Captain contract is exactly seven default tools and keeps the prior six control/query tools;
- dispatch and render tool metadata point to the same MCP Apps resource, while UI refresh calls only the render tool;
- UI writes dynamic data through DOM `textContent`, not dynamic `innerHTML`;
- Qoder ACP and CodeBuddy SDK observation callback regressions pass;
- `git diff --check` passes.

## Sandbox limitation / live gate

This Linux build sandbox does not currently contain the `mcp` Python package, and package installation could not be completed because the environment could not resolve/reach PyPI. Therefore imports that instantiate the real FastMCP server cannot be executed here.

This also is not the user's Windows Codex Desktop host. **No claim is made that the iframe visually rendered in Windows Codex Desktop in this sandbox.** The implementation and fallback contract are preserved for live acceptance.

## Windows first-experience acceptance steps

From the v1.0.9 repository root:

```powershell
python -m agent_runtime.cli init
python .\skills\tp-voyager-captain\install_codex_desktop.py
codex plugin marketplace add .\skills\tp-voyager-captain\integrations\codex\local-marketplace
```

Then:

1. Fully restart Codex/ChatGPT Desktop after MCP/plugin metadata changes.
2. Open Plugins and select **TP-Voyager Local**.
3. Install **TP-Voyager Observability**.
4. Start a **new Codex task/session**.
5. Confirm the `tp_voyager` Captain surface contains seven tools, including `render_voyager_panel`.
6. Dispatch one bounded TP-Voyager task. Confirm the Agent presence card appears from that dispatch result and is pinned to the returned `task_id`.
7. Confirm the card visibly changes state and shows Crew/model.
8. Expand Conversation and verify Provider-visible assistant output appears while/after the Crew runs.
9. Expand Timeline / Files / Usage and compare against the terminal `task_result` / Evidence.
10. Verify completed state is visibly green and failed state visibly red on suitable test cases.
11. If the current Codex Desktop build does not render MCP Apps UI, inspect the structured `render_voyager_panel` result and record the host limitation. Do not classify structured fallback alone as a successful visual-render acceptance.
