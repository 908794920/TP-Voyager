## Scope closure

This increment closes all five requested items in one version; no implementation item is deferred.

### 1. Truthful panel sync

- Opening/resuming the MCP Apps card enters the presentation-only `syncing` state and shows `正在同步`.
- It immediately calls the read-only `render_voyager_panel` with the exact current selector before presenting task state.
- Visibility resume, page show, window focus, and manual Refresh follow the same path.
- The UI contains no call to `task_dispatch`, `task_resume`, or `task_cancel`.
- Durable Task state remains the source of truth.

### 2. Canonical terminal answer and independent windows

- Assistant conversation events are stored in a dedicated bounded stream separate from high-frequency activity events.
- Terminal detail reads the durable structured task result and prefers its canonical final answer.
- A bounded Timeline can no longer evict/crop the canonical terminal answer.
- Timeline rows aggregate consecutive duplicate safe activities.
- Visible answer formatting preserves spaces/newlines/Markdown semantics.
- `TP_VOYAGER_CREW_OUTCOME_JSON` is stripped from both live Conversation projection and canonical terminal prose, then parsed into a user-facing result card.

### 3. Chinese result-first panel

- First screen is result-oriented: 状态 / 执行单元（Crew） / 执行模型 / 任务 / 耗时 plus 结论 / 关键依据 / 风险 / 下一步.
- 完整回答 / 执行活动 / 文件变更 / 用量 are independent foldouts.
- Empty sections are hidden; process details are collapsed by default.
- Duplicate top message/conversation summaries were removed. Common status/activity/tool labels and host invocation prompts are localized to Chinese.
- Dynamic text is rendered with `textContent`; answer text uses pre-wrapped whitespace.
- Prompt/system/secret/raw tool output/absolute host path/hidden reasoning remains excluded.

### 4. Explicit concurrent presentation groups

- `task_dispatch` accepts optional `presentation_group_id` and each dispatch still creates an independent Task.
- The group id is persisted only through existing bounded Session routing metadata; no new table or lifecycle is introduced.
- `render_voyager_panel` accepts exactly one selector: `task_id`, `presentation_group_id`, or explicit `task_ids` (maximum 16).
- Group lookup uses exact membership only and never recent/global task or fuzzy `correlation_id` heuristics.
- Group projection returns exact child task ids plus each child's state/Crew/model/duration/safe summary and independent result/activity/files/usage projection.
- Single-task rendering remains compatible.
- Regression covers independent Qoder + CodeBuddy dispatches in the same presentation group.

### 5. One Codex plugin / one Captain Skill

Current shape:

```text
@TP-Voyager
└─ $tp-voyager:captain
```

- Current plugin source is `integrations/codex/local-marketplace/plugins/tp-voyager/`.
- It is skills-only, contains no `.mcp.json` / `.app.json`, and exports exactly one `captain` Skill.
- Existing `tp_voyager` remains the only MCP Runtime/control boundary and the Captain surface remains exactly seven tools.
- The plugin Captain Skill is the canonical behavioral source. Repository root `tp-voyager-captain/SKILL.md` is only a legacy migration shim.
- The old `tp-voyager-observability` source remains in the repository as migration evidence and is not advertised by the current repository marketplace.
- Installer detects/preserves old installed global Skill and old plugin and reports explicit cleanup steps; it does not silently delete them.
- Current-plugin file drift triggers Codex CLI remove/add cache refresh when CLI is available.
- A new Codex conversation/session is required after host-facing install/update.

## Windows / Codex Desktop live acceptance gate

This sandbox cannot launch the user's Windows Codex Desktop, Qoder CLI, or CodeBuddy CLI. The implementation is complete, but the following environment-specific acceptance must be executed after applying the increment on the Windows host.

1. Run the v1.0.9.2 installer from the repository and confirm it reports current plugin `tp-voyager`, existing MCP registration, legacy detection, and `new_conversation_required` when host-facing state changed.
2. Fully restart Codex Desktop when requested and open a **new conversation**.
3. Verify the new `$tp-voyager:captain` Skill and the existing seven `tp_voyager` Captain tools are available.
4. Dispatch a task, allow it to finish, then reopen/restore its card. The first visible state must be `正在同步`, followed by the latest completed result; an old cached `running` snapshot must never appear as current truth.
5. Run a high-frequency task with a long final answer. The completed card must show the complete canonical final answer even when Timeline exceeds 200 events, with Markdown/newlines preserved and no raw `TP_VOYAGER_CREW_OUTCOME_JSON` line.
6. Confirm completed first screen is Chinese/result-first and execution activity is collapsed; empty file/usage sections are absent.
7. In one programmatic parent call / `Promise.all`, dispatch one Qoder and one CodeBuddy Task with the same fresh `presentation_group_id`. Even if Codex Host renders one card, that card must list both exact child task ids and their independent state/result details.
8. Confirm Refresh on both single/group cards only calls read-only `render_voyager_panel` and never creates/resumes/cancels a Task.
9. Validate the new plugin before cleanup. Then explicitly remove/uninstall legacy `tp-voyager-observability` and remove/delete the legacy standalone `tp-voyager-captain` Skill directory if they are still installed. Do not remove unrelated marketplace entries or user files.
10. Restart/open another new conversation and confirm Codex plugin page has only the current `TP-Voyager` plugin and the MCP/task flows still pass.

## Explicit legacy cleanup reference

Only after Step 1–8 succeeds:

```text
codex plugin remove tp-voyager-observability@<marketplace> --json
```

If the old material is only a leftover directory rather than an active CLI registration, first confirm Codex no longer references it, then remove only:

```text
$CODEX_HOME\plugins\tp-voyager-observability
$CODEX_HOME\skills\tp-voyager-captain
```

The installer intentionally does not perform these deletions.
